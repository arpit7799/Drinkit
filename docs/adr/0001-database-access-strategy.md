# ADR 0001: Database access strategy

- Status: Accepted
- Date: 2026-08-25
- Scope: Phase 1 database foundation

## Decision

Use SQLAlchemy 2.x with an asynchronous PostgreSQL engine (`asyncpg`) for FastAPI request handling and a separate synchronous PostgreSQL engine (`psycopg`) for Alembic migrations and Celery-style workers. Use PostgreSQL as the authoritative transactional store. Keep transaction ownership in application services; repositories only query and persist within a caller-owned session.

Use UUIDv4 primary keys generated by Python and timezone-aware PostgreSQL timestamps. Use deterministic SQLAlchemy naming conventions. Introduce only one domain-neutral persistence primitive now: a transactional outbox table for future reliable event publication.

## Reason

FastAPI's request path is asynchronous, and asyncpg prevents ordinary database I/O from blocking the event loop. Celery tasks and Alembic are synchronous processes, where a synchronous psycopg engine is simpler and avoids creating event loops inside workers. Explicit dual drivers share one metadata model and one PostgreSQL source of truth without forcing every runtime to use the same execution style.

Quick-commerce workflows will eventually need short, explicit transactions around inventory, reservations, orders, and payments. Service-owned transactions make commit/rollback behavior visible and preserve the option to use row locks or isolation levels at the workflow boundary. A durable outbox is compatible with PostgreSQL transactions and prevents a future broker/Redis from becoming authoritative.

UUIDv4 is available on the supported Python baseline, avoids enumerable public IDs, and is straightforward to generate across processes. UUIDv7 is deferred until the runtime baseline and measured ordering/indexing benefits justify it.

## Alternatives considered

### Fully synchronous SQLAlchemy

This would align naturally with Celery and simplify the initial code, but async FastAPI handlers would need threadpool boundaries for every database operation or risk blocking the event loop. It remains a valid option for a lower-throughput service, but not the preferred request-path default here.

### Fully asynchronous SQLAlchemy

This would optimize request handling but makes migrations and synchronous workers less ergonomic. A synchronous adapter would still be needed for Alembic and Celery, so the chosen split is more explicit and operationally predictable.

### SQLite for development and tests

Rejected as a PostgreSQL substitute. SQLite differs in locking, types, partial indexes, JSON behavior, and constraint enforcement. Unit tests are database-free; integration tests use real PostgreSQL.

### Redis as reservation or event authority

Rejected. Redis can accelerate reads and coordinate short-lived work, but critical inventory, order, financial, and compliance state must survive Redis eviction/restart and be protected by PostgreSQL transactions and constraints.

### Integer or UUIDv7 identifiers

Sequential integers expose cardinality and are harder to safely expose externally. UUIDv7 offers locality and temporal ordering, but the current runtime baseline and absence of a measured need make UUIDv4 the lower-risk foundation.

## Trade-offs

- Two engines mean two driver configurations and two connection pools, but the split matches the execution environments and keeps migrations/workers robust.
- Async sessions require discipline around `await` and cannot be passed into synchronous Celery code; worker code must use the sync session boundary.
- UUIDv4 indexes are less insertion-local than time-ordered IDs. This is accepted for Phase 1 and should be revisited with production measurements before very large append-heavy tables.
- The outbox adds a table and future operational responsibility. It is justified because reliable event publication is central to inventory/order workflows, while its publisher is intentionally deferred to a later phase.
